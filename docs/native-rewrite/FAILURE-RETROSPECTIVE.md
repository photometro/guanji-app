# #258–#260 原生化失败复盘

## 结论

失败不是 Compose 无法一比一迁移，而是迁移过程把“重写页面”当成了“视觉等价移植”，并允许入口、宿主、组件、测量、动画和验收各自演化。WebView 源码足够作为规格，但此前没有把它转换成逐状态、逐组件、逐几何约束的可执行契约。

## 1. 架构问题

### 多个可见宿主

`MainActivity`、`NativeShellActivity`、`NativeHomeActivity`、`NativeRecordActivity` 等同时存在。Tab、首页、记录、日历并非同一棵 UI 树，而是通过 Activity 跳转拼接。

后果：

- #258 的 Tab 无法自然成为 #259/#260 的共享根组件；
- 调试时会打开占位壳、页面 Activity 或 WebView 中不同的一个；
- 返回栈不是 WebView 原来的页面/Sheet 层级；
- 系统栏、insets、窗口背景和动画按 Activity 各自计算；
- 出现两个“原生界面”和用户看到空页面的情况。

### 透明 Overlay Activity

记录页用透明原生 Activity 叠在 WebView 上方，日历/Sheet 又在独立宿主中模拟原页面。

后果：

- 背景阴影、半透明壳和内容卡片形成三层；
- 顶部白条和底部不贴底；
- 遮罩与 Sheet 无法复现同一页面内的独立时序；
- 页面看似“弹出”，实质是窗口切换。

## 2. 规格问题

### 只抄了大结构，没有抄完整约束

卡片、标题、图表和按钮被看作功能块，但没有逐项冻结：

- font family、font weight、font size、line height、baseline；
- padding、margin、gap、最小/最大尺寸；
- 圆角、阴影、描边、玻璃层级；
- 图标 path、viewBox、stroke、尺寸和对齐；
- 滚动区域、固定 footer、安全区；
- 空、少量、密集、长文案、两位数字、大字号等状态。

因此出现“布局大致相似，但每个元素都不一样”。

### 用自建契约反向证明自建实现

旧 `GuanjiVisualContract.kt` 和验证脚本部分常量来自原生实现本身，而不是 WebView CSS/浏览器 bounds/真机截图。这样脚本可以全绿，但只是证明代码符合自己写的值，不能证明它符合 WebView。

## 3. Compose 默认行为泄漏

此前实现没有系统性清除 Compose/Material 默认行为：

- ripple/pressed overlay；
- 内容选中时缩放；
- 默认文字行高与最小触控尺寸；
- 固定宽高造成徽标数字裁切；
- 默认弹簧或同步动画替代 WebView 时序；
- `AnimatedVisibility` 父级变化破坏 `BoxScope` 底部对齐。

这些正是 Tab 黑色半透明覆盖、文字像被圆形裁切、图标文字缩放、日历卡片全屏和徽标数字偏下的直接来源。

## 4. 业务与 UI 没有隔离

迁移记录页时同时触碰 WebView 记录偏好和入口逻辑，导致 `quick` 模式下“就现在/补记”的主次关系被改坏。页面移植不应重定义业务语义，也不应让原生未完成页反过来改变 WebView 稳定路径。

## 5. 验收闸门为什么没有阻止

旧闸门存在五个结构性缺口：

1. 它检查“类和文件存在”，没有先否定多 Activity 架构；
2. 它把 WebView v4.2.1 写成基线，和真正要回到的 v4.1.5 不一致；
3. 它能确认截图/JSON 存在，但不能证明截图来自当前目标入口和同一状态；
4. 它没有阻断“功能完成但视觉未验收”被标成完成；
5. 它在页面实现之后补建，无法阻止早期架构已经走偏。

## 6. V2 必须吸收的规则

- 单一可见宿主：所有原生页面、Tab、Sheet 均在 `MainActivity/NativeRoot` 内。
- WebView 与 Native 同时存在只表示两条可切换实现，不表示两层同时显示或两个 Activity 并行。
- 每个版本只迁一个节点；当前节点未签收，不得创建下一页占位实现。
- 每页先做 WebView 测绘，再写 Compose；不能从旧原生截图或旧 token 反推。
- 每次验收都验证入口身份、前台 Activity、页面 route、Tab 唯一性、返回栈和系统栏。
- 视觉差异必须列为缺陷，不能用“原生风格不同”解释。
- 洞悉内容与信息架构改版推迟到原生视觉等价完成后。

## 7. #274 共享 Tab 迁移的专项复盘

### 实际暴露的问题

虽然 #274 最终已修复并签收，但实施过程中先后暴露出以下问题，后续页面迁移不得再次依赖人工记忆：

1. 外层 Tab 宽度、页面左右边距、胶囊圆角、内部 padding 和选中层尺寸与 WebView 不一致；一度出现原生 Tab 铺满屏幕。
2. 原版 SVG 图标未完整复用，文字字号/行高/基线不一致，窄屏和大字号下出现文字裁切、圆形裁切和显示不全。
3. Compose/Material 默认 ripple、pressed overlay、内容缩放和弹簧行为泄漏，产生黑色半透明覆盖、图标文字缩放和不应有的回弹。
4. 透明 Compose 宿主与 WebView 背景叠加，在魅族真机出现白色横线、层级错误或阴影丢失；阴影曾被错误地当作卡片边框或第二层壳处理。
5. 经典、深色、玻璃三种状态的所有权没有在最初冻结：原生 Tab、WebView Tab、玻璃材质桥和 blur 滑块一度互相覆盖，导致玻璃/深色显示与原版不一致。
6. 只验证了静态文件、截图或错误入口，未始终证明截图来自当前真机入口、同一 route、同一主题和同一状态；因此会出现“验证通过但用户看到的是另一套界面”。

### 根因到防再发规则

| 根因 | 后续强制规则 |
| --- | --- |
| 从原生实现反推尺寸 | 只能从 v4.1.5 WebView CSS、DOM bounds、SVG 和同设备截图生成契约；实现不能反向生成基线 |
| 所有权不清晰 | 每个视觉区域必须登记 owner；同一状态只能有一个可见 Tab/页面/Sheet，旧节点同时 `display:none`、不可点击并退出无障碍树 |
| 经典与玻璃混迁 | #275–#280 NativeRoute 只接管经典/普通模式；玻璃仅由 WebView 对照，禁止原生玻璃材质和双层渲染 |
| 默认行为泄漏 | Compose 明确关闭 ripple、pressed overlay、scale、默认最小尺寸和 spring；动画只允许契约中登记的属性、时长和缓动 |
| 窗口/insets 未冻结 | 使用同一 `MainActivity/NativeRoot`、同一安全区和 viewport；禁止页面级 Activity、透明 Overlay 和自定义系统栏偏移 |
| 验收证据不对应入口 | 每次证据必须同时记录包名、版本、前台 Activity、route、主题、dataRevision、Tab 数量、Sheet 层级和采样时刻 |

### 后续任务的阻断条件

- 任何尺寸、圆角、图标、字体、基线、阴影、分割线或图表线宽没有 WebView 来源，任务不得进入 Compose 实现。
- 出现白条、黑色覆盖、文字/图标缩放、未登记回弹、内容裁切、全屏 Sheet、底部悬空或双 Tab 时，必须退回当前节点修复，不能以“原生差异”放行。
- 玻璃模式不得因为经典模式迁移而改变；#281 删除旧 JS 核心后，玻璃请求统一回落到已验收的 Native 经典界面，玻璃原生版本另立任务并重新测绘。
- 公共 Tab/主题/宿主改动必须重跑 #274 的浅色经典、深色经典、窄屏、大字号、手势导航、魅族底部横条、重启和玻璃 WebView 回退用例。
